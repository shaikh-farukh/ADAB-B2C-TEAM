4. B2C flow — do not break this chain

Customer search→Approved listing/PDP→Cart→Checkout→Payment→orders→seller_orders per seller→Accept → Process → Pack → Ship→Shipment/Tracking→Customer + Seller + Admin notifications→Delivered→Review OR Return→Refund→Inventory adjustment→Seller settlement
Product gate: Seller creates seller_listings → submits → Admin/Karan approves/rejects/requests changes → product_approval_history records decision → only eligible/published listing becomes customer-visible.

Multi-seller order: orders is the customer parent order; seller_orders splits responsibility by seller. Customer sees the parent order, seller sees only its seller_order, Admin sees the hierarchy.

Notification propagation: domain transaction → outbox_events → notification processor → notifications → Socket.IO/WebSocket live push. REST/database remains the source of truth.

Conflict-prevention rules without Git/PR instructions

  1. Single writer per business domain: only the named owner changes the domain service, repository and write endpoints. Other developers consume the published DTO contract.
  2. Single writer per table: every table has one write owner. Read access can be used by other portals through repository/service APIs, not by adding duplicate write logic.
  3. Shared API contract is append-only: a developer may add a new endpoint only under the owner of that domain. Do not modify another owner's endpoint shape silently.
  4. No duplicate business logic: there is one checkout engine, one payment/refund engine, one order engine, one shipment engine, one return engine and one notification pipeline.
  5. DTO boundary: cross-portal communication uses stable DTOs such as ProductCardDTO, ListingDTO, CartDTO, CheckoutPreviewDTO, OrderDTO, SellerOrderDTO, ShipmentDTO, ReturnDTO, PaymentDTO and NotificationDTO.
  6. Events instead of direct cross-domain writes: use outbox_events for ORDER_CREATED, ORDER_ACCEPTED, ORDER_SHIPPED, RETURN_REQUESTED, REFUND_COMPLETED, LISTING_APPROVED and similar events. The receiving domain reacts without editing another owner's tables.
  7. Migration isolation: a migration touching an owned table belongs to that table's owner. Cross-table migrations are coordinated as a single contract change rather than six independent edits.
  8. Integration adapters are isolated: third-party provider code lives under integration adapters; portal modules call an ADAB interface, never provider-specific code directly.
  9. Frontend isolation: seller-web, customer-web and admin-web have separate component trees. Shared UI primitives are read-only contracts unless a designated shared-UI owner is assigned.
  10. No waiting: each developer builds against typed mock DTOs and contract fixtures first, then swaps the Axios implementation to the real endpoint. A missing backend must not block frontend progress.

Business-flow invariants — these must never be broken

Customer search → only APPROVED/PUBLISHED listing → cart → stock validation/reservation → checkout preview → payment provider → payment verification/webhook → one parent orders record → one seller_orders record per seller → seller accepts/processes/packs → shipment created → carrier tracking → customer + seller + admin notification → delivered → review OR return → return inspection → refund engine → inventory adjustment → settlement/payout.

Critical rule: A payment provider callback can never directly change an order to delivered. A carrier callback can never create a refund. A customer UI can never directly mark an order as shipped. Each state transition is owned by its domain service and emits an event for downstream consumers.

Enterprise non-functional API checklist

  • JWT/access token + refresh token rotation; OAuth state/PKCE where applicable; secure cookie/session policy.
  • RBAC + resource ownership checks on every protected API.
  • Idempotency keys for checkout, payment, refund, shipment creation, webhook processing and settlement actions.
  • Rate limits for login, OTP, search suggestions, checkout, coupon validation and support/chat endpoints.
  • Structured errors with stable codes, field validation errors and correlation IDs.
  • Pagination, filtering, sorting and cursor pagination where high-volume feeds require it.
  • SQL parameterization, transaction boundaries, row locking for inventory and financial operations, and no cross-domain direct table writes.
  • Outbox + queue processing for notifications, imports, exports, reports, search reindex and external sync jobs.
  • Webhook signature verification, replay protection, event deduplication and dead-letter handling.
  • Observability: request IDs, structured logs, metrics, latency/error dashboards and integration execution logs.
  • Security: secret manager, encrypted provider credentials, signed URLs, file type/size checks, malware scanning hook for uploads, audit trails and PII minimization.
  • Testing: Jest/RTL for frontend, Jest/Supertest for backend, contract tests for every endpoint, integration tests for payment/shipping/webhooks and one full marketplace E2E flow.
